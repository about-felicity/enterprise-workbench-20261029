# 豆包2采集内存防护部署验收

2026-10-20，北京时间11:16左右核验。用户要求优化模拟器 Java 堆溢出及采集卡住问题。

## 原因与边界

- 历史10月15日日志确有 `java.lang.OutOfMemoryError`，目标/增长上限512MiB。10月20日09:22的退出记录则是 Android `LOW_MEMORY`，不能混称 Java 堆溢出。
- 容器此前由3GiB调至4GiB，内存加交换额度7GiB。容器额度不会改变 App 自身512MiB Java堆上限。此次未修改App堆、关闭Android低内存保护或清空App数据。
- 防护属于采集端监测和安全恢复，不能宣称消除了第三方App内部的内存泄漏。

## 已部署

- `redroid-deploy/native_memory_guard.py`：每60秒采样实际Dalvik HeapAlloc、Native HeapAlloc、App PSS及容器工作集；核验LARGE_HEAP标记选择正确堆上限，不把PSS当Java实际分配，不将可回收缓存全部算作工作集。
- `geo-monitor-deploy/config/native_memory_policy.json`：本次只启用豆包2。Java实际分配达到上限85%、容器工作集85%或App PSS达到容器额度65%，同一进程连续两次超阈值才申请维护；参数可配置。
- 仅在问题完成、全部结果获得真实入库回执、无待补读/未知发送/异常任务且用户未暂停时维护App。维护不发问题、不清登录或队列。采样失败、进程已变化时不按旧压力重启。
- 冷却15分钟，6小时最多3次；维护意图先落盘，计数跨worker重启和每日批次保留。超过预算进入退避。
- 根据对应进程退出原因区分LOW_MEMORY和其他崩溃；仅当对应PID的崩溃缓冲在退出时间附近含Java OOM时才归类Java堆溢出。
- 内存状态和14天数值采样保存在 `/home/user/redroid-doubao/memory/doubao-hpe14-account2/`，不清理回答、历史或待回传数据。面板已显示实际Java堆指标和维护状态。
- 豆包UI登录检查由每个3秒循环改为新问题立即检查、其余最多每30秒检查；未改变元宝检查逻辑。
