# scrcpy 浏览器输入和回显延迟优化

2026-10-17 已发布，需刷新投屏页面获取新客户端。适用于测试机和以后新打开的两路正式登录投屏。

## 修改

- 原客户端每次按下、抬起和每个按键都排队等待一次 HTTP 回复；公网下同一次点击会产生两次串行往返，甚至被 Android 当成长按。现在短点击一次请求内注入 down/up，长按和拖动保持正常触摸顺序。
- 连续文本合并，输入分批有序发送，每批至多 16 个已校验事件；拖动只保留尚未发送的最新移动位置，滚轮合并，队列有上限。失败清空未发送队列并要求重连，不重试或重放未知结果的文本、验证码和点击。
- 控制 socket 和两层 Python HTTP handler 开启 TCP_NODELAY。H264 输入解码明确单线程，JPEG 每帧 flush；multipart 每帧立即写下一个 boundary，静止页面仍保活。
- 支持的浏览器通过 fetch 流解析完整 JPEG 后立即绘制 canvas，只保留最新待绘制帧并释放 ImageBitmap，避免浏览器原生 img multipart 显示额外缓冲。旧浏览器保留原生 img 兼容路径。底层仍为真实 scrcpy 编码流，没有 ADB 截图轮询。
- 视频断开可自动重连；不自动重复发送输入。登录风控、人工验证、verifying、ready 的原有处理保留。
- 公网实测还有超过旧 5 秒阈值的状态往返；状态查询阈值改为 15 秒，暂时断网不会覆盖已知风险提示或重放输入。真实公网风险验收首轮因此超时，修正后复测通过。

## 实测与边界

同一台服务器浏览器、同一测试机，通过实际公网入口模拟按下和抬起两次点击：

| 客户端 | 每次点击请求数 | 两次输入确认耗时 |
|---|---:|---|
| 原版 | 2 | 6113.6 / 8431.3 ms |
| 新版 | 1 | 3440.8 / 4319.5 ms |

这是两个样本的 A/B 对比，不能当作所有设备、地区、时段的性能保证。当前公网线路依然有数秒往返延迟，优化没有消除物理链路延迟。

服务器浏览器经本地入口的控制确认约 8–16 ms。菜单像素变化（包含 App 菜单动画）原版约 484–539 ms，新 canvas 显示约 358–442 ms。只改 ffmpeg flush/线程的中间两轮仍约 446–535 ms，未把这些中间结果宣称为显著改善。这些是服务器本地入口的测量，不代表用户电脑的实际网络 RTT。

客户端回归：101 次字符输入合为 2 次请求且文字顺序一致；572 次拖动事件合为一次有序 down/latest-move/up 请求；短点击一次请求；失败零重试。JPEG 逐字节拆分、跨块标记、多帧合块、最新帧释放检查通过。Python 2 项批输入协议/拒绝嵌套及超限、5 项既有沙箱检查通过。

桌面/手机真实只读视频加隔离控制夹具验收：输入、风险/人工验证/verifying 不关闭、ready 自动关闭、无溢出或 JS 错误。公网真实禁言测试机显示日期并保持投屏，手动控件可用，无自动问题发送。测试中的菜单操作仅在测试机，不修改产品数据、账号登录或正式队列。

旧夹具预期每次点击必有独立 touch 事件，与新 click/batch 不符，已改为校验展开后的有序语义；旧风险 QA 的固定 worker PID 断言还发现了真实登录失效，未忽略该事件。首次本地 PowerShell 生成夹具脚本转义失败后改用独立脚本，最终夹具通过。100/100 当前源文件映射一致。
