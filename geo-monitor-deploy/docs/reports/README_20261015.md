## 网页采集与回传

复制内容创作服务器当前已安装的采集器及依赖到独立 venv，保留已有网页采集修复。内容创作原 venv 和运行目录没有替换，四个正式服务的 PID 和启动时间核对未变。

新 CLI 增加 `--max-new-captures 1`，每取得一个持久化结果后主动让出通道，恢复时仍使用原 21 题及原批次指纹。百度和文心用 `flock` 串行访问浏览器，并共用持久化搜索时间状态，至少间隔 60 秒；分别使用独立 profile、队列、结果目录。DeepSeek 使用 9514 端口及独立 profile，间隔 600 秒；内容创作仍使用 9414。

回传 `POST /api/v1/models/{model}/results`，DeepSeek 对应 `deepseek`；文心与百度卡片使用现有 `wenxin` 模型，以 `capture_mode`、`capture_label`、`source_device` 区分，绝不拿文心结果冒充百度结果。

本地 SQLite 保存原始记录；完整正文、全部可见信源、引用入口和原始采集结果保留在 GEO 的 `capture_result` 中。先持久化 outbox，再发送；请求 ID 严格使用原 GEO 多模型接收器的内容哈希合同。网络重试只重复同一 envelope，不重复提问。

接收器创建的 done 文件只有其自身用户可读。新增状态服务提供带原接收器 Bearer 鉴权的只读回执接口 `/api/receipts/{model}/{request_id}`，只允许 deepseek/wenxin 与 64 位十六进制 ID；没有开放任意文件读取。采集桥接器只有核对存储 run ID、正文长度、完整性、信源数量和逐条标题/URL、未隔离后，才保存 processed 回执。现有接收服务无需重启。

百度每题保留五轮观测；只对同一问题下正文、完整信源、引用入口均相同的结果去重。重复观测映射到首个请求 ID 和回执，不再次入库或排队分析。文心六轮、DeepSeek 三轮不在桥接器中合并。`unavailable` 单独计数，不伪装成完整正文或 processed。

GEO 原产品分析 worker、跨模型公平调度的信源正文 worker 会继续消费新数据；processed 只证明正文和信源入库，不代表所有下游分析已完成。

## 当前阻塞与恢复

DeepSeek 原内容创作会话也在实时检查中返回 `login_required`，不是仅复制后副本失败。原巡检记录从 10 月 14 日已处于该状态。新 GEO 队列 63 条均未发出，状态页显示“等待 DeepSeek 登录”。不能声称 DeepSeek 已实采或取得 processed。

用户在原内容工作台完成一次登录后，空闲时运行迁移脚本（使用 user 身份）：

```sh
sudo -u user /opt/monitor/geo-capture/venv/bin/python /home/user/redroid-doubao/migrate_session_geo.py
```

脚本先持有原 collector.lock，只在原浏览器空闲时检查；源端 ready 才在内存中导出 cookie/storage，再向独立 GEO 浏览器注入。没有明文打印会话、没有重发提问。迁移记录 target_ready=true 后，再启动原 GEO DeepSeek 服务，不重建批次或重置队列。需要重新实测一题并核验 processed。

## 安全维护与回退

新采集通道的批次目录可创建 `pause.json`。桥接器让当前采集完成并核验回传后，才退出并标为 paused；不要直接终止正在发送/生成的浏览器来更新代码。重启留下的 capturing 仍按原 journal 标为 needs_attention，不盲目重发。

恢复前确认 status=paused、worker_pid 为空、没有 capturing/needs_attention，然后移除该批次 pause.json 并启动相应服务。只恢复原批次，不删除 SQLite、发送证据、outbox 或 receipts。

回退新集成时，先按上述方式排空新通道，再停新增采集器与状态服务；恢复豆包 unit 的备份或移除本次 geo-group.conf 后 daemon-reload。原 GEO Docker Compose、模拟器数据卷、内容创作服务不依赖新目录，不需要跟随回退重启。保留新增队列和日志以便核对，不能把回退当作清理重复发送证据。
