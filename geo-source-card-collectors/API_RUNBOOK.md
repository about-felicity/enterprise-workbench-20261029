# DeepSeek Flash 每日文章生产

分类、信源分析、文章写作和语义审稿由 Linux 服务器上的 DeepSeek Flash API 完成。Windows 仅同步已验收文章、显示桌面面板并提醒网页登录状态。原来的飞书和本地豆包任务、MCP 控制程序已停用并移出运行代码。

## 每日执行

北京时间默认 05:00，`geo-editorial-scheduler.service` 按 settings.json 启动当天采集，面板可修改时间。旧的 01:00 timer 已禁用。使用原始问题，不追加“附上信源”。每题每平台只采集一轮。DeepSeek 每题开启全新空会话，百度和文心每题重新搜索；DeepSeek 网页提问间隔可设为 300—600 秒，默认 600 秒；百度 AI 卡片与文心卡片走同一个串行浏览器，分别保存正文、来源和完整性状态。网页登录每 180 秒巡检，采集期间不争抢浏览器。

Scrapling 抓取信源正文，保留原 URL、最终地址、实际正文、失败原因和证据。网络抓取失败不伪造正文，验证页面不当作文章。只有抓取成功且属于配置中的中国大陆媒体或内容平台的来源进入分类；内容平台的自媒体不自动视为记者或独立权威证据。

所有平台采集及信源抓取完成后，API worker 立即处理队列，不再使用另一个写作时间门槛；资料迟到则等待资料，不用昨天素材冒充今天采集。未完成旧批次仍在其原日期下继续，文件不会被重新贴上今天日期。每类默认最多十篇，面板可设 1—100 篇，少于三篇独立素材的类别不凑数。类别和结构来自当日内容，不能保证每天类别数相同。

## 分析与写作

2026-10-09按用户要求启用 balanced-editorial-v1：普通选购建议、主观偏好、明确假设场景和结构润色作为建议，不因缺少逐句引用直接退稿；带限定的一般价格档位观点保留提醒，不视为已核实事实。具体产品参数、功效用法、虚构亲测、错误计算与缺变量推算仍拦截。程序提醒存入 draft_review.json 的 warnings，模型润色建议存入审稿 suggestions。已撤回的旧版本不会因规则放宽直接恢复，须通过新的修订交付。

1. 分类请求读取每个有效来源的算法节选（完整原文另存），给出主题与体裁、逐条来源、连续原文证据和写作角度。程序要求来源全部有归属，引用逐字存在于正文。字符 TF-IDF 与余弦相似度合并相近转载。
2. 同一类别的研究请求综合至少三个来源，提取至少六条知识、争议或风险，保留来源归属与条件，并设计至少四节的新提纲及创新角度。来源主张始终标记为未独立核验。
3. 写作请求使用独立上下文，只读取经过检验的知识概括与结构，不接收原文全文。结合当篇角度写完整文章和事实、章节映射；程序输出 Word。来源为实测或榜单时，借鉴消费比较维度，不虚构作者亲测、效果数据或竞品资料。
4. 程序核对正文长度、较长复制片段、产品限制、输入与输出哈希、Word 与 Markdown 一致性。另一次 API 请求独立审稿，检查类别、结构、创新、产品衔接、虚构测试、事实依据和消费者文章可读性。
5. 不合格交付形成明确的返工票据，默认最多一轮自动返工；仍不合格进入待处理。只有全部检查通过的文章进入 `approved`，Windows 下载后再次逐文件验证哈希。

目前产品资料允许的表述以运行目录 `product.json` 的 `approved` 为准。品牌提供资料和产品名称不等于功效得到独立证明。身份或规格可以自然用于相关消费场景并表达商业关联；其他事实不能由模型补造。审稿是模型与程序检查，不等于人工或实验核验，媒体 API 发布尚未接入。

后台服务：`geo-editorial-coordinator.service` 负责验收；`geo-editorial-api-worker.service` 负责 05:00 后的 API 执行；`geo-editorial-session-watch.service` 负责登录检查；`geo-editorial-capture.timer/service` 负责采集。Windows `GeoEditorialArchiveSync` 每60秒同步文章，登录后启动，关闭面板不停止同步。API 生产不依赖 Windows 开机；电脑离线时合格文章留在服务器，重新登录后补下载。

安装示例：先安装 wheel 的 `writing` 依赖和 Chromium，再将运行资料与密钥放在源码外，执行：

```bash
sudo python deploy/install_server.py --base /home/user/geo-editorial --runtime /home/user/geo-editorial/runtime-api --user user --key-file /home/user/geo-editorial/secrets/deepseek.key --enable-capture
```

本机安装可使用 `pip install .[desktop]`，然后运行 `deploy/install_archive_sync.ps1`，或使用已有桌面发行包。SSH helper 来自当前部署配置；迁移到别的主机需替换 helper、运行根目录和远端 Python 路径，不需要改业务算法。

## 故障与完成判断

API 请求先保存发送意图再调用。完整 JSON 响应落盘后可在程序重启时继续生成文件；响应缓存绑定请求内容，不能拿旧响应处理新输入。完整交付回执最后提交，重复恢复不再调用模型或覆盖已交付 Word。

断网、超时或 HTTP 5xx 无法确定服务端是否已处理时，当前执行停止并标记待核验；不盲目重发。明确收到但格式错误或截断的响应保留证据并按有限返工流程处理。401、余额不足、服务端限制等问题需要处理凭据或服务状态，不能靠无限重试解决。

完成须同时满足：票据属于当前执行、输入没有变化、预期文件完整且哈希正确、确定性检查通过、审稿通过、最终归档回执存在。日志中的阶段 accepted 不代表整篇已完成；看 day.json 的 accepted_articles 和 approved 中的最终回执。

运维只操作本项目命名的服务；原有八个业务容器和 Redroid 不参与此流水线。不要删除正在执行的票据、发送意图或浏览器日志。需要清理时先归档终止批次，源码内的 build、缓存和旧控制模块集中移至 intermediates。

## 无人值守验收

六小时计时必须在完整试跑质量通过、当天三平台采集完整、生产 Word 已验收且本机已同步后开始。条件未满足只记录等待，不能提前计为通过。观测检查服务健康、网页登录、队列错误、API 未知请求、资源和文章哈希；发生异常保存证据，最终报告写明观测窗口和实际结果。

单次 API 调用成功或一篇文章通过不等于六小时验收通过。完整六小时窗口和每日真实 05:00 触发仍需实际运行记录证明。


## 费用保护（2026-10-09）

默认单篇 0.20 元、每日 10 元、开发测试累计 0.50 元，可在“计划与费用”调整。未获得用户新的数值选择时先使用这组保守默认值。单篇预算包含失败调用及分类、同类研究费用；共享费用暂按全额归入每篇的上限检查，不依赖“未来一定会产出十篇”的乐观分摊。

全部阶段关闭思考，独立审稿仍是单独请求。小规模分类/研究/写作/审稿输出上限分别为6000/4800/4200/3500 token。超过24条信源时，分类先用代表性来源制定类别，再按每组12条逐批覆盖；类别规划2600、分组归属1600 token。逐批缓存并验证，不因单次输出太长而漏来源。研究与分类先用本地去重、相关性排序和原文节选压缩输入；保留所有有效来源的URL，不以摘要冒充未抓到的正文。研究输出紧凑知识单元，由本地程序恢复任务标识、URL和逐字证据；审稿使用当前稿件句子ID，稿件哈希由不可变输入绑定，不要求模型抄写哈希。

2026-10-09后续迭代中，按用户“实在不行可以提高预算”的授权，服务器当前单篇限额调为0.35元；每日10元、开发测试累计上限现为1.00元。默认配置仍为0.20元。审稿的实际错误与可选润色建议分开保存，实际错误仍阻断交付。

相同来源、产品、提取策略版本的同类研究通过校验后复用。每篇使用不同角度，写作与独立审稿仍分别进行；缓存失效依据源数据和策略版本，不按文件名猜测。

每次 POST 前，在 SQLite 事务中按输入 UTF-8 字节保守上界和最大输出预留费用，使用官方核验的高峰人民币价格（输入未命中 2 元/百万，命中 0.04 元/百万，输出 8 元/百万）。返回 usage 后按实际 token 更新费用估算，只有整个请求时间段确定属于闲时才应用半价；跨高峰、时钟异常或时间未知保持高峰估算。节假日未自动计算，按普通工作日保守处理。平台实际扣费以账单为准。报价版本超过30天暂停，需重新核对价格后维护代码中的价格版本，不能擅自跳过。

网络结果未知的预留不释放、不自动重试；缺失 usage 保留全额预留。HTTP 401/402 明确拒绝时不计成功消耗，需用户完成重新检测及继续动作后才能尝试。预算不足在发送之前暂停，不自动调高额度。原试验目录的费用已迁移到生产账本，以后的 --test-budget 调用共享测试总额，跨日不重置。

输出截断单独记录为 output_incomplete，保留原始输出和 usage，直接暂停，不自动付费重写；重启 worker 也不会把它转换成可重试任务。需要修改输入或输出合同并离线检查后另行验证，不能仅点击继续来重复原请求。

## 暂停与人工恢复

1. 登录检查每180秒；每次发送前再次检查，等待提问间隔期间也检查。明确掉登录会落盘 control.json，所有新提问和 API 请求停止。
2. 发送前确认未按下发送的题目保留 pending。已经尝试发送、结果不明的题目保持 needs_attention，不以“重新登录”作为可以重发的依据。
3. 登录或充值后，点击“重新检测环境”。该操作只检查网页登录及 GET /user/balance，不发问题、不生成文章。
4. 检测通过后五分钟内点击“继续任务”。设置变化或再次暂停会使旧检测失效。只检测不继续不会恢复运行。正在读取的当前页面会安全收尾，不强杀其他服务。
5. DeepSeek与文心为必需采集。百度按用户最新要求作为补充：先展开再判断正文；确实无卡片记no_card，采集失败保留错误并记supplement_unavailable，继续文心。失败补充记录不参与文章分析，也不冒充完整正文。独立CLI默认仍严格，服务器批次显式启用--optional-baidu。

文心导航超时先等待当前页面，仍超时且当前URL与本题目标完全一致才刷新一次；不会刷新其他题目的页面。显式恢复历史失败只允许已诊断的只读搜索错误，DeepSeek未知发送状态不重放。

暂停可跨进程重启和服务器重启保留。调度器恢复原日期批次，已完成题目按持久化 ID 跳过；存在发送状态不明的题目会继续阻塞，需要核对证据，面板不会静默清除它。
